# SignalWorks — design for review

## Purpose
A runnable Python/SQL reliability lab and interactive portfolio case study that lets a visitor introduce an event-processing failure, observe its consequences, recover, and inspect evidence. Target audience: recruiters and technical interviewers evaluating entry-level data engineering work.

## Relationship to existing work
Extend LedgerStream in Kartikeya-Rana-2004/engineering-portfolio, preserving its original module, tests, case study, and provenance. SignalWorks must cite its foundation and describe what it adds. Do not present the existing engine as newly invented work.

## Backend
Use LedgerStream's two local SQLite databases: source orders and transactional outbox; sink projection, receipts, quarantine, and checkpoint. Add a reproducible scenario runner producing a versioned JSON trace for the website. Synthetic order data only; integer cents; no external services or paid infrastructure.

Scenarios: successful processing; exact duplicate delivery; invalid payload with valid routing metadata; crash within the sink transaction and rollback; recovery from the checkpoint; full replay; deletion followed by a stale entity update. Include conflicting duplicate identity and sequence-gap failures in technical verification. Preserve the distinction between source sequence order and entity version order.

Each trace transition records scenario, event identity, source sequence, entity version, disposition, committed checkpoint, quarantine count, current paid-order total, and explanatory text. Capture database state at the relevant commit/rollback boundaries. An injected crash must demonstrate rollback, not merely stop an animation.

## Website
A standalone case-study page suitable for static hosting and linking from the existing portfolio. Near-black backgrounds, warm-white typography, red accents, accessible contrast. Opening content explains the problem, what was built, and how to run it. Include case-study, source, evidence, limitations, and AI-assistance disclosure.

Anatomy Figure: one detailed isometric parcel inspection/sorting machine, 40–80 purposeful parts, four-tone shading, one active accent. Parcels represent events; a receipt mechanism represents committed processing; a rejection tray represents quarantine. The machine is a teaching metaphor, not an infrastructure diagram. Keep a conventional architecture diagram and explanations below it.

Controls: choose scenario, run/step, pause, reset. Provide four prominent presets: duplicate, malformed record, crash/recover, replay. Show committed checkpoint, accepted/current state, quarantine count, and revenue alongside a readable event history. Distinguish committed state from pending work visually and in text.

The public page replays traces generated by the real Python runner. It does not execute Python, contact a backend, or claim live database execution. Caption: “Interactive replay of a recorded local run using synthetic data.” Controls and readouts follow the same selected trace state; animation interpolates between trace states and does not invent results. Provide a command to regenerate traces. Keep monetary values visibly synthetic.

Prefer SVG without shader layers for the explanation. Pause offscreen; honor reduced motion; provide keyboard/touch controls, text equivalents, responsive layout, and a useful static initial state. Avoid combining continuously animated effects around the figure.

## Verification
Backend tests must prove source/outbox atomicity; sink transaction rollback; restart/checkpoint recovery; unchanged state after duplicate/full replay; quarantine behavior; conflicting replay rejection; gap handling; and tombstone protection. Reuse existing tests where they already establish a contract.

Generate traces from actual runs. Check trace schema and invariants and that checked-in traces reproduce from a clean run without nondeterministic IDs/timestamps. Browser checks: controls and counters, reset, keyboard, reduced motion, mobile width, no console errors, static fallback, and offscreen pause. Follow Anatomy geometry/line checks and inspect desktop/mobile screenshots and close-ups in dark and light themes. Record limitations honestly if any check cannot run.

## GitHub integration
Work from the current remote repository in an isolated checkout/branch. Add a signalworks module, tests, trace evidence, demo assets, and docs/signalworks.md following the repository structure. Update the root project index/README to link the new case study and runnable demo. Preserve unrelated changes. Push verified work and create a reviewable pull request under the user's authorization. Do not overwrite the original LedgerStream entry or claim GitHub Pages hosting without verifying deployment configuration.

## Acceptance
A reviewer can run one documented command, reproduce all scenarios and evidence, open the static demo, see why duplicate delivery and recovery preserve correct totals, and follow links to implementation and tests. Any performance claims require measured evidence. No production-scale, Kafka, distributed exactly-once, or live-cloud claims.
